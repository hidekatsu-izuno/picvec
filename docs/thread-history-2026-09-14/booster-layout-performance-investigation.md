# booster-layout.jpg の長時間化調査

以下は修正前の調査記録。今回の修正と再計測は [性能修正](booster-layout-performance-fix.md) を参照。

`booster-layout.jpg` は5770×2058画素（11,874,660画素）。標準設定では1600×571画素の変換後、高精細化が画像全体を原寸で再変換する。その原寸処理のエッジ解析だけで約205秒を要した。最大の負荷は明暗の線を検出する円盤モルフォロジーで、切り出して測ると約126秒だった。

## 確認した経路

1. 最初の処理解像度は1600×571（913,600画素）。高精細化を無効にした変換は、アプリ内計測22.628秒で正常に完了した。出力は1,953,423バイト、7,678オブジェクト。
2. [候補選定](../src/adaptive.rs#L703)で安全な局所候補が残らず、`0 0 5770 2058` の全画面候補を作る。観測した優先度は5.9213で、既定の閾値2.5を上回る。
3. [解像度選択](../src/pipeline.rs#L843)は、拡張範囲が`adaptive_tile_dimension=1400`を超えると原寸を選ぶ。`--max-dimension 1600`はこの分岐の再処理上限にはならない。診断版で`crop=5770x2058 processing=5770x2058`を確認した。
4. 前回追加した局所再利用はこの画像では適用されず、全画面の変換へ進む。変更前のバイナリでも同じ全画面候補・同じ優先度が出た。全画面へのフォールバックと原寸選択は、変更前のコミット`3fa41d2726efb77974a990666f5cd1ab28b85c5f`にも存在する。
5. [子処理の設定](../src/pipeline.rs#L790)で`retain_diagnostics=false`にするため、通常の`--verbose`でも子処理の段階別ログが出ない。重い計算が進んでいても、全画面候補の表示で止まったように見える。

外周の背景判定は約96%のサンプルが許容範囲に入った。今回の全画面候補は「背景色を推定できず、全画素を前景扱いした」ケースではない。

## 原寸エッジ解析の内訳

診断用コピーで段階別の時刻を追加し、原寸RGBと4スレッドでエッジ解析を単独実行した。

| 処理 | 所要時間 |
|---|---:|
| 初期エッジ場の畳み込み | 約11.76秒 |
| エッジ場・非最大抑制・細線化・輪郭プロファイルまで | 累計15.64秒 |
| 周囲の明るさの最大値計算など `dark_ridge_support` | 約31.99秒 |
| メディアル軸による線の抽出 | 約2.16秒 |
| `ridge::strong_branches` | 約143.99秒 |
| エッジ解析全体 | **204.56秒** |

別途`strong_branches`だけを切り出した測定では、全体149.75秒、Hessian応答22.85秒、円盤トップハット約126.05秒となった。上表とは別の実行なので、そのまま加算する値ではない。

| 円盤半径 | その半径での4回の形態処理（累計差から算出） |
|---|---:|
| 11画素 | 約7.21秒 |
| 17画素 | 約17.41秒 |
| 23画素 | 約31.69秒 |
| 34画素 | 約69.75秒 |

エッジ単独のプロセスは正常終了し、CPU時間707.34秒、外部計測の経過時間192.98秒、最大RSS約1.30GiB、major page fault 0、swap 0だった。上表はコード内の`Instant`計測。全体変換の完了時間は今回測っていない。標準設定の全体診断実行は、原寸エッジ解析中に調査用として打ち切った。

## 計算量が増える理由

[ridge.rs の `morphology`](../src/ridge.rs#L277)は、全画素に対して円盤内の点を総当たりし、最大値または最小値を求める。[`top_hats`](../src/ridge.rs#L311)は各半径でこの処理を4回実行する。[半径の選択](../src/ridge.rs#L408)は画像の長辺に比例する。

| 解像度 | 半径 | 各円盤の点数 | 1回のリッジ解析で調べる点数 |
|---|---|---|---:|
| 1600×571 | 3, 5, 6, 9 | 29, 81, 113, 253 | 1,739,494,400 |
| 5770×2058 | 11, 17, 23, 34 | 377, 901, 1653, 3625 | 311,401,083,840 |

点数は`画素数 × 4 × 円盤点数の合計`から計算したもの。CPU命令カウンターの実測値ではない。画素数は約13倍だが、円盤も広がるのでこの処理量は約179倍になる。境界では反射して参照するため、画像端でもループ回数は減らない。

[局所最大値](../src/edge.rs#L1689)も全画素で正方形内を総当たりする。半径11→39、窓23×23→79×79となり、約4.83億点→約741.10億点に増える。実測でも約32秒を消費した。

さらに通常の処理経路では、[領域分割後のcanonical画像](../src/pipeline.rs#L1596)でも`ridge::analyze`を呼ぶ。原画像とcanonical画像は異なるので、そのまま同じ計算結果を共有することはできない。原寸エッジ解析だけを終えても、同種の重い計算が後段に残る。

## 回避方法と修正対象

確認できた回避方法は高精細化を無効にすること。

```sh
target/release/picvec sample/input/booster-layout.jpg /tmp/booster-layout.svg \
  --threads 4 --no-adaptive-refinement
```

1600×571の通常変換を使い、原寸での細字の高精細化を省く。今回生成して確認したファイルは`/tmp/picvec-booster-investigation/no-adaptive.svg`。

修正の優先箇所は以下。

- 円盤の形と境界の反射を保ち、行ごとの区間最大・最小値を共有して、円盤モルフォロジーの重複走査を除く。
- 正方形の局所最大値は、水平・垂直の滑動最大値へ置き換える。
- 全画面候補を原寸へ一度に拡大する経路に、処理量に応じた段階的な解像度選択を設ける。
- 高精細化の開始時に実際の処理解像度を表示し、子処理の進捗を識別できるようにする。

今回は原因調査用のコピーでログを追加した。実装変更の検証や、最適化後の性能測定はまだ行っていない。
