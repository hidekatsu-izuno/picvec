# booster-layout の処理時間修正

## 変更

- 全画面などの大きな adaptive 候補にも `maximum_dimension` を適用する。基底画像と同じ解像度しか得られない候補は、原寸RGBの切り出し・リサイズ・再ベクトル化前に棄却する。小さい局所候補の高精細化は維持する。
- 円盤モルフォロジーを水平区間の和集合として計算する。同じ幅の区間結果を共有し、総当たりの O(Nr²) を O(Nr) にする。円盤の画素集合と画像端の反射を保つ。一度に保持する中間画像は区間幅1種類分で、全幅分の画像は保持しない。
- 正方形の局所最大値は水平・垂直の滑動最大値で計算する。端でのclampを保ち、窓面積に比例する走査をなくす。
- adaptive 子処理を実行するときは、診断ログに入力範囲と実処理寸法を表示する。

上限の適用は処理品質との交換条件を明示する動作変更。全画面を原寸で再変換する場合は、利用者が `--max-dimension` を引き上げる必要がある。上限を変更しない既定設定では、5770×2058の画像を再度原寸ベクトル化しない。フィルター自体の高速化は近似ではない。

## 検証方法

- 円盤と正方形のフィルターを独立した総当たり実装と比較。1画素の画像、非正方形、画像より大きな半径、実画像で使う半径11・17・23・34・39を含む。
- 全画面に誤差がある合成画像で、処理上限に達したadaptive候補が再ベクトル化されず、基底SVGをそのまま返すことを検証。
- 既存の線・透明度・adaptive結合の回帰テストを実行。

- releaseライブラリテスト: **440成功、0失敗、7既存ignore**。`cargo check --release --locked --no-default-features`も成功。
- 車の画像と透過PNG: 旧版と修正版のSVGバイト列、および時間・出力パス以外の診断結果が一致。こちらはビルドと並行実行したため、速度比較には使用しない。

## 時間の比較条件

4スレッド、release、diagnostics有効。修正前の約205秒は原寸エッジ解析**単独**の測定であり、変換全体の所要時間ではない。今回の標準設定の完了時間と割り算して「同じ品質で何倍高速」とはしない。原寸全体の再変換を上限で止める効果と、同じ処理解像度でのフィルター高速化は区別する。

同じ1600×571の変換を高精細化無効で交互に各2回測った結果、修正前22.576秒、フィルター修正後20.362秒（平均、約9.8%短縮）。4回ともSVGは完全一致した。

最終ビルド `target/release/picvec` の標準設定（高精細化有効）は **26.881秒、26.139秒、平均26.510秒**で完了。再ベクトル化した候補は0件、出力は1,953,423バイト・7,678オブジェクトで、従来の1600×571変換とバイト単位で一致した。局所候補探索などの時間は残るため、高精細化無効の20.362秒とは異なる。

再現:

```sh
mise exec -- cargo build --release --locked --features diagnostics
target/release/picvec sample/input/booster-layout.jpg /tmp/booster-layout.svg --threads 4 --verbose
```

[測定値・コマンド・ソースと実行ファイルのハッシュ](booster-layout-performance-fix.json)。調査用計測スクリプトとログは `/tmp/picvec-booster-investigation/` に保存。最終出力は同ディレクトリの `fixed-default-0.svg` と `fixed-default-1.svg`。
