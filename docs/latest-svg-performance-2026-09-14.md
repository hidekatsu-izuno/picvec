# Git最新版SVGに一致する性能修正

品質基準は作業開始時のHEAD `3fa41d2726efb77974a990666f5cd1ab28b85c5f` に登録された `sample/output/*.svg` 全9枚。旧版415d64fの出力への巻き戻しは取りやめ、最新版の塗り・透明度・幾何処理を維持する。再生成結果は見た目だけでなくファイルの全バイトで比較し、完全一致したものだけを `sample/output` に反映する。

最終候補はrelease/diagnostics、自動スレッド数（この環境では10）、各画像300秒の上限で逐次実行する。計測中に別の変換・ビルド・テストを重ねない。6×6のみ `--remove-chroma-key-background` を指定する。CPUなどの条件は[環境JSON](latest-svg-performance-2026-09-14/environment.json)、基準SVGのハッシュは[expected.json](latest-svg-performance-2026-09-14/expected.json)に記録した。

## 主な原因と対応

### 小さな色配列の並列化

塗りの探索内で、最大8,192色の配列を何度もRayonへ投入していた。領域ごとの探索自体も並列化されているため、配列ごとの同期が処理時間を増やしていた。この範囲を逐次変換にし、画像全体の色変換は並列処理を維持した。RGB→OKLabの式、出力順序、浮動小数点の値は変えていない。境界の前後を含むビット一致テストで確認した。

10スレッドの比較では、viewport2の初期塗り探索と内部陰影に計約35秒かかっていた。配列の投入方法を変えることで、同じ10スレッド・同じSVGの全体時間が159.430秒から126.375秒になった。4スレッドの通し比較も行い、その結果を残している。

### 離れた小さなパッチを囲む大きな描画範囲

6×6の線色補正は小さな5パッチだが、離れたパッチの外接矩形が画像の広い範囲を覆っていた。その矩形だけで描画を判定すると、パッチのないタイルでも1,434本の線からなるクリップを再描画する。

通常合成でフィルターのないグループは、子要素の描画範囲の和でタイル・帯域との交差を判定する。線には線幅を含む境界、フィルター付きグループにはフィルターを含む境界を使う。レンダラーの原点・キャンバス・パス・クリップ形状は変えない。

保存済みの同じ6×6基底SVGに対する可視性検証は、修正前94.589秒（10スレッド）、修正後4.632秒（4スレッド）。出力のバイト一致を確認した。この単独検証は全変換時間とは別であり、基底変換と部分精細化を含む時間は通し計測で確認する。

### 再解析・再描画・検証の重複

- 未変更のSVG部品の解析、パスの正規化、構造線の輪郭、塗りの統合判定を正確な入力条件で再利用する。参照される定義や属性が変わる場合は再解析する。
- 独立した通常合成のレイヤーを、元と同じ描画範囲で描いてから保存する。透明度のある描画列を別レイヤーへまとめ直さない。保存後の完全なゼロRGBAの余白だけを省く。
- タイルのキャッシュを担当スレッドではなくタイル番号に紐付ける。再描画コストの高い独立レイヤーを優先し、保持量を制限する。
- 可視性の証拠は、要素を省いた画素を後続描画まで追跡して得る。先行要素の削除で影響する証拠は無効化し、従来の省略描画へ戻す。薄い・小さいという理由で削除しない。
- 穴の検証は同じ基準画像に対して行い、許容誤差を累積させない。不一致候補の再利用には正確なパス文字列と、不一致を実測した帯域を使う。最終結果は通常レンダラーで全帯域の1倍・4倍RGBAを確認する。
- 残差候補の透明度がゼロとなる範囲では、検証済みの塗りが変化しないことを利用する。候補の選択順序や画質閾値は維持する。
- 極値窓と円盤モルフォロジーをスライディング処理へ変更し、Gaussian畳み込みは各出力のf64加算順序を保ってSIMD化する。

## スレッド数と検証順序

自動スレッド数は「検出した論理CPU数の半分、最低1」という規則を維持し、上限を4から10に変更する。20論理CPUのこの環境では10となる。`--threads` の明示指定は引き続き可能。4スレッドでは6×6の基底変換が165.914秒で終わったが、36個の原寸部分精細化の途中で300秒に達したため、部分精細化を減らす代わりに利用するCPU数を増やす。4スレッドと10スレッドの測定を同条件の比較として混ぜない。

直前の不一致帯域を先に調べる試作も行ったが、viewport2で短縮を確認できなかったため取り消した。

部分精細化は、従来の固定サイズの組ごとの完了待ちをやめ、終了した処理枠から次の候補を開始する。同時実行数はCPU数と従来のメモリ見積もり・4GiB予算で制限し、最大10とする。候補の評価結果は元の順序に揃えてから集計し、順位付け・採否・SVG合成は従来の処理を使う。入れ子の並列処理でも同時実行数を超えず、結果の順序を維持することをテストした。

## viewport2の原寸候補

Git版viewport2は1600×1067の基底SVGで、追加の原寸SVGを含まない。局所候補がない場合に、分離の根拠がない写真まで無条件に全面原寸変換へ送っていた分岐を変更した。背景・前景の分離根拠がある大きな図版は、引き続き原寸変換と通常の採否評価を使う。boosterの原寸5770×2058も維持する。

この候補生成の変更は、未知の入力に対して候補集合を変える。あらゆる入力で旧候補集合との一致を主張するものではなく、今回の品質基準は登録済み9画像のSVGとの一致である。

## 検証

- `cargo test --offline --release --features diagnostics --lib`: 449件成功、失敗0、通常実行では8件除外。
- `cargo check --offline --no-default-features --all-targets`: 成功（既存の診断用フィールドのdead-code警告あり）。
- 全9 SVGのXML検査: mask要素・属性なし、グループopacityなし、塗りの透明度0かつストロークなしの面も0。詳細は[検証JSON](latest-svg-performance-2026-09-14/verification.json)。
- 保存済み6×6基底SVGの可視性検証: 出力バイト一致。
- 同じSVGの断片描画を通常レンダラーと比較: 1倍・4倍の各3帯域でRGBA完全一致。
- 回帰テストで検出した水平・垂直線の境界の問題は、線幅を含む境界を使う修正で解消した。以前試したクリップ境界による描画範囲縮小は、Wikipediaロゴの穴に差分が出たため撤回している。

全9画像が300秒以内に完了し、すべて基準SVGとバイト単位で一致した。SVG maskなし。過去の中間測定JSONは同名ディレクトリに保存し、最終成功結果とは分ける。
